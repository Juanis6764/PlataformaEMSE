1. Resumen del sistema

La Plataforma EMSE es una aplicación web institucional dividida en un frontend Next.js, una API REST NestJS y una base PostgreSQL administrada mediante Prisma. Actualmente el trabajo funcional está concentrado en control de acceso y panel administrativo. La estructura de notas existe en la base como preparación futura, pero el flujo académico de notas todavía no debe considerarse implementado.

Alcance actual: autenticación en dos pasos, sesiones seguras, usuarios, cadetes, cursos, roles, permisos, secciones, jerarquías, asignaciones académicas estructurales y auditoría. No incluye todavía registro, aprobación, ponderación o publicación de notas.

2. Arquitectura y recorrido de una solicitud

Usuario en navegador ↓ interacción Página/Componente React (frontend/src) ↓ servicio Axios + Bearer token Controller NestJS ↓ Guard JWT → Guard de permisos → DTO validado Service NestJS (reglas de negocio) ↓ PrismaService / transacción PostgreSQL ↑ respuesta { data, meta } o entidad Frontend actualiza únicamente la tabla/pantalla afectada

Los controllers definen URLs y reciben datos. Los DTO verifican que esos datos tengan formato permitido. Los guards impiden el acceso sin sesión o permiso. Los services contienen las reglas de negocio. Prisma convierte operaciones TypeScript en SQL seguro.

5. Historia completa de migraciones

Una migración es una modificación versionada de la estructura de la base. Se ejecutan en orden. No son datos de prueba y no deben borrarse. prisma migrate reset destruiría y recrearía la base, por eso no se usa con los 363 cadetes.

1) 20260518194003_control_acceso

Creó el núcleo original: Usuario, Rol, Seccion, Permiso, RolPermiso y Sesion. Añadió CI, nombres, contraseña, estado booleano, relaciones de rol/sección, claves primarias, índices únicos y claves foráneas. Fue la primera versión RBAC (control por roles y permisos).

2) 20260519033200_doble_verificacion

Creó CodigoVerificacion para el segundo factor. Cada código pertenece a un usuario y tiene fecha de creación, vencimiento y marca de uso.

3) 20260519034304_doble_verificacion

Añadió correo a Usuario y originalmente lo hizo único. Esto permitió usar correo como destino OTP.

4) 20260630160707_estructura_usuarios_notas_auditoria

Fue una ampliación mayor. Creó enumeraciones de grupos, estados, gestión, notas y tipos de sección; convirtió el estado booleano de Usuario a EstadoUsuario; amplió OTP y Sesion; agregó jerarquía organizacional; creó Curso, GestionAcademica, Nota, CertificadoNota, LogAcceso y AuditoriaAccion. También insertó secciones y cursos históricos iniciales.

Consecuencia histórica: esta migración creó cursos llamados 1ER_ANIO, 2DO_ANIO, 3ER_ANIO. El seed posterior creó “Primer Año”, “Segundo Año” y “Tercer Año”. Por eso existen cursos duplicados por orden. El frontend actual selecciona dinámicamente el curso que realmente contiene cadetes, sin hardcodear IDs.

5) 20260713201318_redisenio_cadete_responsable_academico

Separó los datos específicos del cadete fuera de Usuario. Creó Cadete, JerarquiaUsuario, PermisoSeccionRol e HistorialPassword. Añadió primer_inicio. Creó EstadoCadete y AreaAcademica. Esta separación evita mezclar datos generales de identidad con grado, arma, curso y egreso.

6) 20260713202824_redisenio_final_academico

Reemplazó ResponsableAcademico por AsignacionAcademica, incorporando el nivel OPERADOR/JEFE, vigencia y área. Añadió indicadores de módulos académico y documental en Usuario.

7) 20260713202950_redisenio_final_academico_historial

Permitió asignaciones de JEFE sin curso (id_curso nullable) y creó HistorialCursoCadete para conservar promociones y estados anteriores.

8) 20260713211022_agregar_refresh_historico_y_rtr

Creó RefreshHistorico para Refresh Token Rotation. Permite detectar reutilización de tokens, revocarlos y cerrar sesiones comprometidas. Añadió índice único para asignaciones de jefe sin curso.

9) 20260713220637_permitir_correo_compartido_cadetes

Eliminó la unicidad global de correo. Esto permite que varios cadetes de prueba compartan un buzón OTP. El CI continúa siendo la identidad única.

Infraestructura común

ClaseQué hace

Módulo Autenticacion

AutenticacionController publica iniciar-sesion, verificar-codigo, refresh, logout, me y cambiar-contrasena. AutenticacionService valida bcrypt, aplica rate limit, genera OTP de seis dígitos, guarda su HMAC por diez minutos, pide el correo, crea sesiones y tokens, rota refresh tokens, detecta reutilización, registra logs y cambia contraseñas conservando historial.

DTO: LoginDto (CI/contraseña), VerificarOtpDto (CI/OTP), RefreshDto (refresh token) y CambiarContrasenaDto (actual/nueva).

Módulo Correo

CorreoService crea el transporter SMTP, verifica conexión y envía el HTML del OTP. Registra messageId, accepted y rejected. En EMAIL_TEST_MODE sólo muestra el OTP si NODE_ENV=development, pero intenta igualmente el envío real. Un fallo se propaga; no responde éxito falso.

Módulo Usuarios

UsuariosController: listar, detalle, crear, actualizar, estado, rol, sección, supervisor y restablecer contraseña. UsuariosService: bcrypt, CI único, creación transaccional con jerarquía, paginación, búsqueda, protección del único ADMIN, revocación de sesiones al cambiar privilegios y recuperación temporal.

DTO: CrearUsuarioDto; ActualizarUsuarioDto; FiltrarUsuariosDto; CambiarEstadoDto; CambiarRolDto; CambiarSeccionDto; CambiarSupervisorDto.

Módulo Cadetes

CadetesController/Service: listado paginado, búsqueda, creación atómica Usuario→Cadete→Historial, detalle por ID/CI, edición, cambio de curso, egreso e historial. Para primer año fuerza arma nula; para segundo/tercero exige arma. La transacción evita un Usuario huérfano si falla Cadete.

DTO: CrearCadeteDto, EgresarCadeteDto, ActualizarCadeteDto, CambiarCursoDto y FiltrarCadetesDto.

Roles, Permisos, Secciones y Cursos

ServiceReglas
RolesServiceCRUD lógico, protege ADMIN, evita eliminar roles usados y reemplaza permisos en transacción.
PermisosServiceCRUD lógico y nombres únicos.
SeccionesServiceCRUD, árbol jerárquico, protección de secciones oficiales y dependencias.
CursosServiceCRUD, orden, protección de cursos oficiales y conteo de cadetes para resolver duplicados históricos.

JerarquiasService

Administra supervisor/subordinado, evita auto-supervisión y ciclos, conserva fecha_fin al revocar y permite consultar supervisores, subordinados e historial.

AsignacionesAcademicasService

Lista, crea y revoca responsabilidades. OPERADOR requiere curso; JEFE no lleva curso y cubre el área completa. Evita duplicados y múltiples jefes activos del mismo ámbito. Es estructura administrativa; no procesa notas.

AuditoriaService

Registra acciones, datos antes/después, IP y user-agent; lista auditoría y logs de acceso con filtros.

Clases Module

Cada clase terminada en Module agrupa controller, service e imports. No contiene reglas; su función es decirle a Nest cómo inyectar dependencias.

8. Autenticación, OTP y seguridad

1. POST /autenticacion/iniciar-sesion {ci, contraseña} 2. findUnique(ci) → bcrypt.compare 3. verificar ACTIVO y correo 4. randomInt → OTP 6 dígitos 5. HMAC-SHA-256 → CodigoVerificacion (10 minutos) 6. await SMTP sendMail 7. POST /autenticacion/verificar-codigo 8. marcar OTP usado → Sesion + access token + refresh token 9. si primer_inicio=true → pantalla cambiar contraseña 10. nueva contraseña bcrypt + historial + cierre de sesiones
  • CI inexistente ejecuta bcrypt ficticio para dificultar enumeración.
  • Cinco fallos activan bloqueo temporal en memoria.
  • OTP tiene máximo de intentos y se invalida al usarse.
  • Si SMTP falla, el OTP queda invalidado y el endpoint falla.
  • Refresh Token Rotation detecta token reutilizado.
  • Los secretos viven en variables de entorno, no deben aparecer en documentación o commits.

10. Panel administrativo actual

Cadetes

  • Conteos actuales: 116 primer año, 130 segundo, 117 tercero; total 363.
  • Los IDs no están hardcodeados: se consultan cursos y se elige el curso relacionado con cadetes por orden.
  • Primer año oculta arma y envía null.
  • Segundo/tercero exigen Inf., Cab., Art., Ing., Com., Int., Mot., San., MB. u otra.
  • Búsqueda por CI/nombre/apellido, filtro de estado, edición, suspensión/reactivación y recuperación.
  • Historial y botón Egresar están ocultos actualmente por decisión de interfaz, aunque el backend conserva las capacidades.

Administrativos

Alta por grupo, rol y sección; listado paginado; estado; supervisor; recuperación de contraseña. Las acciones refrescan sólo los datos de la pantalla.

Roles y permisos

CRUD de catálogos y asignación/quita del arreglo completo de permisos de un rol. El guard consulta la relación real al autorizar.

Asignaciones

Permite configurar JEFE u OPERADOR por área y curso. Se mantiene para no rehacer estructura cuando llegue el módulo de notas.

11. Seed y estado de datos

El seed valida listas, crea roles, secciones, permisos, relaciones, cursos, gestión, administrador y 363 cadetes. Sus upserts de usuarios existentes no deben sobrescribir contraseñas. Para cadetes existentes actualiza datos identificativos, no su hash. La creación inicial usa bcrypt.

El seed es idempotente, pero no debe usarse como mecanismo de recuperación de contraseñas. Las recuperaciones usan scripts/servicios específicos y entrada secreta.

Comandos frontend

Pruebas actuales

Existen specs para app, autenticación, usuarios, roles, permisos y secciones. En la última verificación: 11 suites, 28 pruebas aprobadas; backend y frontend compilaron. Swagger permite pruebas manuales autenticadas.

Reglas de mantenimiento

  • Nunca ejecutar migrate reset en una base con datos reales.
  • No borrar migraciones aplicadas.
  • Crear cambios estructurales con una migración nueva.
  • No imprimir contraseñas, tokens u OTP fuera del modo autorizado.
  • Usar transacciones cuando se escriben varias tablas.
  • Refrescar una tabla después de mutar, no recargar todo el dashboard.
